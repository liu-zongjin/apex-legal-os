# 公开案例检索超时修复

## 复现与原因

按用户截图中的“买受人已收楼或选择继续履行后，再主张解除合同不予支持”原问题验证。并行诊断中，维基文库API直连约4.9秒返回200，而HTML阅读页和系统代理均连接超时。因此浏览器可访问与程序失败可以同时发生；先等代理/阅读页、锁定失败路径及分层超时累加是程序缺陷，不能直接归因于网站不可用。

旧实现还有三处放大失败的逻辑：外层超时将已累积案例替换为空数组；搜索摘要必须同时包含所有争点条件，过早丢弃线索；把“收楼或继续履行”拆成同时满足的条件及把空搜索当成网络错误。

## 修复

- 案例专用网络适配器在短延迟后并行尝试直连与现有系统代理，采用先成功的路径，取消剩余工作；成功路径下一次失败时仍能切换，不永久锁定。真实429不继续切换以规避限流。
- API搜索、批量正文优先；HTML/REST作为不同路径的兜底。每个请求使用总截止时间，不累加多层完整等待。
- 来源预算结束后返回已取得的候选与诊断，不清空整批结果。
- 搜索摘要按部分争点召回，法院正文和引文的严格核验保持不变。收楼、收房、继续履行属于同一可选事实组。
- 空搜索记录为零命中；来源提示去重并简化，技术原因放入可展开的检索记录。
- 未调整系统代理设置、未接入专业案例MCP、未修改原生壳或发布安装包。

## 实测

1. 使用截图原问题，通过实际模型服务 Flash进行计划、公开检索、正文读取及观点判读，约57.9秒完成。召回21件去重候选，输出6件取得案号、法院、原文链接及法院说理的候选；专业案例MCP调用设置为立即报错，本次没有触发。
2. 这6件中没有被确认的直接支持案例；结果如实标为部分相关或观点未核，没有将“拒绝收房”冒充“已收房”，也没有宣称已完成该命题的精准召回。
3. 连续三次真实API查询分别约6.8、2.7、3.8秒完成，每次返回3条命中，随后批量正文接口读取成功。
4. 60项相关测试通过，覆盖慢代理接替、失败路径切换、总截止时间取消、部分结果保留及“或”条件。APEX extended运行1312项测试通过，27项跳过；最终小幅提示文案调整后重跑相关测试及fast检查。
5. 本地服务确认源码为current、无需重启。没有通过点击真实用户历史的“重新生成”覆盖既有回答；真实模型验证使用临时检索缓存完成，不操作用户业务数据库。

## 边界及恢复

本次解决超时链路和过早过滤；不保证互联网始终连通，也不证明已找到全部符合该法律命题的裁判。无直接支持时必须如实说明。
